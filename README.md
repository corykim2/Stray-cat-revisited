# 🐈 Stray Cat Community — 3년 만의 배포

2022년 해커톤에서 제작한 뒤 한 번도 배포하지 않은 채 방치했던 Django 프로젝트를, 컨테이너로 감싸 실제 클라우드 환경에 배포한 기록이다.

> 원본 저장소: https://github.com/corykim2/Stray_cat_Hackathon
> 애플리케이션 코드는 팀원들과 공동으로 작성했으며, 이 저장소에서 새로 추가한 것은 컨테이너화 · 배포 · 운영 구성이다.

---

## 프로젝트 개요

길고양이의 위치와 상태를 지도에 기록하고, 사용자들이 함께 관리하는 커뮤니티 웹 서비스다. 기능 자체는 2022년에 완성되어 있었으나, "배포해봤자 무엇이 되겠는가"라는 판단으로 로컬 환경에만 둔 채 마무리되었다.

이 저장소는 해당 프로젝트를 다시 꺼내어 배포와 운영의 관점에서 재구성한 것이다. 목표는 기능 추가가 아니라, "로컬에서 동작하는 것"과 "서비스로 제공되는 것" 사이의 차이를 직접 확인하는 데 있었다.

## 배포 과정에서 마주한 문제들

3년 전의 코드를 다시 실행하는 과정은 곧 "환경이 코드의 일부였다"는 사실을 확인하는 과정이었다.

### 1. 코드는 그대로였으나 실행되지 않았다

`import imp` 한 줄이 Python 3.12에서 오류를 일으켰다. `imp`는 3.12에서 제거된 모듈이며, 3년 전의 코드 자체에는 문제가 없었다. 변한 것은 코드가 아니라 실행 환경이었다. 로컬 파이썬 버전을 변경하는 대신, `python:3.10-slim` 이미지로 환경을 고정하는 방식을 택했다.

### 2. 이 코드는 애초에 리눅스에서 실행될 수 없었다

`from asyncio.windows_events import NULL`은 Windows에서만 존재하는 모듈을 import하는 구문이었다. 실제로 사용되지 않는 한 줄이었으나, 이로 인해 리눅스 서버에서는 첫 줄부터 실행이 중단되었다. 즉 이 프로젝트는 배포를 하지 않은 것이 아니라, 배포가 불가능한 상태였던 것이다. 팀 구성원 전원이 Windows 환경이었고 다른 환경에서 실행한 적이 없었기에, 3년간 이 사실을 인지하지 못했다.

### 3. 실행 환경이 어디에도 기록되어 있지 않았다

`requirements.txt`가 존재하지 않았다. 대신 가상환경 폴더가 통째로 커밋되어 있었으며, 그 설정 파일에는 팀원의 노트북 절대경로가 그대로 남아 있었다. 환경을 공유한 것이 아니라, 한 대의 컴퓨터 상태를 저장소에 올려둔 셈이었다. 커밋된 가상환경으로부터 의존성을 역으로 복원하여 `requirements.txt`를 재구성했다.

### 4. 개발 서버가 대신 처리하던 작업이 있었다

`DEBUG=False`로 배포하자 정적 파일(CSS)이 전혀 적용되지 않았다. 개발 환경에서는 `runserver`가 정적 파일 서빙을 대신 처리하고 있었으며, 이를 당연히 동작하는 기능으로 간주하고 있었다. `collectstatic`으로 파일을 수집하고 `whitenoise`로 서빙하도록 구성했으며, `runserver`를 `gunicorn`으로 교체했다.

### 5. 재배포 시 사용자 데이터가 소실되었다

컨테이너를 재생성할 때마다 업로드한 사진과 계정 정보가 모두 사라졌다. 데이터가 컨테이너 내부에 저장되어 있었기 때문이다. Docker Volume을 연결하여 데이터를 컨테이너 외부로 분리했으며, 그 결과 동일한 재배포 명령에도 데이터가 유지되었다.

> 이 외에도 인코딩(cp949 ↔ UTF-8), 줄바꿈 문자(CRLF ↔ LF), CPU 아키텍처(x86 ↔ ARM), 시간대(UTC ↔ KST), 외부 API의 도메인 등록 등 "환경이 다르다"는 사실은 배포 과정 내내 여러 층위에서 드러났다.

## 아직 해결하지 못한 문제들

배포는 완료했으나, 그 과정에서 새롭게 떠오른 질문들이 더 많았다.

- 서버가 중단되어도 이를 인지할 방법이 없다. → 모니터링
- 서버를 삭제할 경우, 동일하게 재구성할 방법이 기억에 의존한다. `docker run` 명령을 수작업으로 입력했을 뿐이다. → IaC(Infrastructure as Code)
- 볼륨은 해당 서버 내부에 존재한다. 서버 자체가 소실되면 데이터는 어떻게 되는가. → 오브젝트 스토리지 / 백업
- `rm → run → migrate` 절차를 매번 수작업으로 수행하며, 종종 일부를 누락한다. → CI/CD
- 설정을 코드에서 분리했으나, `.env`는 서버마다 수작업으로 생성한다. 서버가 다수일 경우 이를 어떻게 관리하는가. → 시크릿 관리

이 질문들이 앞으로 학습하고자 하는 주제이다.

## 실행 방법

```bash
# 1. 이미지 빌드
docker build -t straycat .

# 2. 환경변수 준비 (.env.example 참고)
cp .env.example .env
#   DJANGO_SECRET_KEY 생성:
#   docker run --rm straycat python -c "import secrets; print(secrets.token_urlsafe(50))"

# 3. 볼륨 생성 후 실행
docker volume create straycat-data
docker run -d --name straycat -p 8000:8000 \
  --env-file .env -v straycat-data:/data straycat

# 4. DB 초기화
docker exec straycat python manage.py migrate
```

접속: http://localhost:8000

필요한 환경변수는 [`.env.example`](.env.example)에 정리되어 있다.
